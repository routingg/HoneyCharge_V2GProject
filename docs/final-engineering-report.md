# HoneyCharge V2G — Final Engineering Report

## 1. Repository architecture discovered

Next.js 16 (App Router) served through the `vinext` adapter on Cloudflare
Workers/Pages (Vite 8 build). Two pre-existing, working front ends: a
grid-operator dashboard (`components/HoneyChargeApp.tsx`) and a consumer
mobile SPA (`components/mobile/**`), both backed by a single-day,
fixed-schedule rule-based scheduler (`lib/services/v2gScheduler.ts`)
operating over 32 synthetic fleet vehicles. No mobility prediction, no
calendar integration, no AI/Gemini usage, no guaranteed-SOC decomposition,
no baseline-vs-adaptive comparison, and no validation dashboard existed.
Full detail in `docs/implementation-audit.md`.

## 2. Existing code reused

- `Vehicle`/rule-based scheduler pattern in spirit only — the new domain
  model is deliberately separate (see §3) rather than overloading the
  existing single-day `Vehicle` type.
- Tailwind CSS variable palette (`--ink`/`--muted`/`--panel`/`--line`/etc.
  from `app/globals.css`) reused for the new `/validation` dashboard's
  visual style, for consistency with the existing brand.
- Existing test convention (`node --test` + on-the-fly TS transpilation)
  extended rather than replaced — new domain tests use the same
  `node --test` runner via `tsx` (already a transitive dependency, no new
  dependency needed for tests).

## 5. Architecture decisions

- **Additive domain module, not a rewrite.** `lib/domain/**` has no
  dependency on `lib/types.ts` or the existing scheduler. This was a
  deliberate choice to satisfy "preserve all functioning HoneyCharge
  features" while still building a technically defensible new
  architecture.
- **Six-layer pipeline** (CONTEXT -> PREDICTION -> SAFETY -> OPTIMIZATION
  -> EXECUTION -> VALIDATION), never collapsed into one service or one AI
  prompt — see `docs/architecture.md`.
- **The domain layer has zero framework dependencies.** It runs
  identically under `node --test` (via `tsx`) and inside the browser
  bundle — the `/validation` dashboard runs the real prediction/SOC/
  scheduling pipeline client-side; only the Gemini calendar call crosses
  to a server API route, keeping the API key server-only.
- **The fixed-SOC baseline reuses the adaptive scheduler function**,
  parameterized with a static floor instead of the computed guarantee —
  one implementation, two configurations, so "fixed vs. adaptive" can't
  silently diverge into two different code paths.

## 6. Mobility prediction algorithm

Recency-weighted (14-day half-life) same-weekday historical departure
distribution, blended with an optional calendar signal (location-presence
heuristic, or Gemini classification when available) via confidence-weighted
averaging with an agreement bonus / disagreement penalty. Trip energy is
predicted independently from Gemini: median recent distance × median
recent consumption. Full detail: `docs/mobility-prediction.md`.

## 7. Gemini integration design

Single `AIService` interface (`lib/services/ai/types.ts`); `GeminiProvider`
is the only file importing `@google/genai`. Structured JSON output via
`responseJsonSchema`, independently re-validated. Full detail:
`docs/gemini-architecture.md`.

## 8. Gemini fallback strategy

Every failure mode (disabled, missing key, timeout, rate limit, invalid
JSON/schema, network/server error) logs a structured `AI_FALLBACK` event
and returns a deterministic heuristic — never throws to the caller.
Verified with zero live network calls in the automated suite
(`tests/domain/ai-gemini-provider-disabled.test.mjs`: fallback returns in
<500ms for all three `AIService` methods with `GEMINI_ENABLED` unset).

## 9. Guaranteed SOC algorithm

`tripRequirementSoc + userReserveSoc + uncertaintyMarginSoc`, floored at
the user's hard minimum, margin from a 5-tier confidence table (5–22
percentage points). Full detail: `docs/guaranteed-soc.md`.

## 10. V2G scheduling method

Rolling 24h/30-min-slot greedy heuristic: hard-minimum protection first,
then forced departure-preparation charging, then opportunistic
grid-signal-driven charge/discharge only when SOC exceeds the guarantee.
Full detail: `docs/v2g-optimizer.md`.

## 11. Safety mechanisms

Explicit 6-state safety state machine
(`NORMAL`/`CONSERVATIVE`/`CHARGE_REQUIRED`/`VEHICLE_UNAVAILABLE`/
`STALE_DATA`/`EMERGENCY_RESERVE`), plus an independent post-hoc schedule
scanner (`countSafetyViolations`) that doesn't trust the scheduler's own
bookkeeping. Both are pure functions, unit-tested directly.

## 12. Vehicle simulator

`SimulationVehicleAdapter` — deterministic SIL simulation (seeded PRNG,
tick-based time), 9 injectable event types, command-safety enforced at
the simulator level independent of the scheduler. Not HILS — no hardware
in the loop. Full detail: `docs/simulation.md`.

## 13. Calendar / Apps Script readiness

`NormalizedCalendarEvent` carries only start/end/allDay/location
(opt-in); verified by `tests/domain/calendar-normalize.test.mjs` that no
other field survives normalization. Apps Script reference (not deployed):
`examples/apps-script/**`, design doc: `docs/apps-script-integration.md`.

## 14. Validation scenarios

§36–§42's core scenarios (normal commuter, early departure, calendar
update, low SOC, insufficient history, high consumption, stale telemetry)
plus charger/vehicle disconnect are all implemented as injectable
simulation events and covered by tests or manual dashboard verification —
see `docs/vcycle/06_simulation_test_spec.md` for the exact mapping and the
one identified gap (no automated multi-event-sequence test).

## 16. Adaptive vs. fixed SOC results

Three genuine backtest runs (synthetic 30-day history, real numbers, not
estimates) — see `docs/vcycle/07_validation_results.md` for the full
tables and reproduction command. Summary:

| Run | Fixed floor | Fixed discharged | Adaptive discharged | Guarantee rate (both) | Safety violations (both) |
|---|---:|---:|---:|---:|---:|
| 1 (99.8kWh) | 50% | 243.37 kWh | 340.64 kWh (+40%) | 100% | 0 |
| 2 (77.4kWh) | 50% | 313.68 kWh | 407.34 kWh (+29.9%) | 100% | 0 |
| 3 (77.4kWh) | 95% | 1.76 kWh | 407.34 kWh (huge %, see note) | 100% | 0 |

**Honest caveats, not overclaimed conclusions:**
- All three runs happen to show 100% mobility guarantee rate for both
  strategies at this seed/config — that's a property of this particular
  synthetic scenario, not proof the adaptive strategy always wins on
  safety. `tests/domain/backtest.test.mjs` explicitly includes a case
  (Run 3's config, fixed floor 95%) demonstrating the fixed strategy can
  match or exceed the adaptive strategy on guarantee rate — the harness
  is not tuned to make adaptive win (§46).
- Run 3's "huge %" improvement figure is a genuine finding about the
  improvement-percentage metric's fragility near a zero baseline, not a
  meaningful claim — see `docs/vcycle/07_validation_results.md`'s
  interpretation section.
- These are all against **synthetic, clearly-labeled** trip history for
  one demo vehicle profile. No claim is made about real-world drivers.

## 17. Gemini integration validation

Not performed against a live Gemini API — no network access to the real
endpoint in this sandbox. The fallback path (which the system relies on
by default, `GEMINI_ENABLED=false`) is fully tested. The A/B/C comparison
described in §52 (history-only vs. +calendar vs. +Gemini) is supported by
the domain layer's design but not yet wired into a batch comparison
endpoint — see §20 below (limitations).

## 18. Current limitations

- No live-Gemini integration test (network access unavailable here).
- `GEMINI_MODEL` default (`gemini-2.5-flash`) unverified against the
  current Gemini model lineup — verify before production use.
- Env var plumbing for `GEMINI_API_KEY` on actual Cloudflare Pages
  production deploys (as opposed to local `vinext dev`, which does load
  `.env`) is unverified — needs a real deploy + Pages dashboard env var
  check.
- No automated multi-event-sequence simulation test (each event type is
  tested individually; the dashboard supports arbitrary sequences,
  manually verified only).
- No automated A/B/C Gemini-mode comparison endpoint (§52) — the pieces
  exist (`predictDeparture`'s `geminiCalendarAnalysis` parameter,
  `GeminiProvider`) but aren't wired into a batch experiment yet.
- `vinext start` (local production-mode server) did not correctly serve
  static assets in this sandbox (404s on `/assets/*`) — appears to be a
  local-emulation limitation of Cloudflare Pages' asset-serving behavior
  rather than an application bug (assets serve correctly under
  `npm run dev`); worth a real Cloudflare Pages deploy check before
  assuming production parity.
- `npm audit` reports 16 vulnerabilities (6 moderate, 10 high) introduced
  transitively by `@google/genai`'s dependency tree — not reviewed in
  depth as part of this implementation; recommend `npm audit` review
  before production deploy.
